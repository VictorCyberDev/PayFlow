## E-7 in more detail

This is the item behind the defect reported as "the same goal planned once and
failed the next". It was never about the goal.

The experiment that settled it, run against the deployed site with one identical
goal string:

| Arm                          | Result        |
| ---------------------------- | ------------- |
| 8 requests, 20 seconds apart | 8 / 8 succeed |
| 8 requests, concurrent       | 7 / 8 succeed |

Identical input, different outcome as a pure function of request rate. That rules
out the model failing on the content and names the provider's per-minute window.

What was fixed in code: a 429 now causes PayFlow to wait the interval Groq states
in `retry-after` and ask once more, bounded by half the request's own 20-second
budget and abandoned the moment the deadline passes. The same applies to a provider
5xx and to a generation that missed its own schema. The retry is only defensible
because the call has no side effects — `governPlan` re-derives every total and
stamps authorization `NONE` — so a second attempt cannot double anything.

What was **not** done, and why: lowering `max_completion_tokens` looked like an
obvious throughput win, and an earlier note in this work guessed it was the cause.
Groq's published rate-limit documentation does not support it — the burst failed on
the 8th request, which is consistent with roughly 1K actual tokens per request
against an 8K window, not with a 4K reservation per request (that would have failed
on the 2nd). The guess was dropped rather than shipped.
