# Standards alignment notes

Status: DRAFT, 2026-11-02.

**No certification, no audit and no attestation is claimed.** PayFlow has not been assessed by any third party against NIST SSDF, OWASP ASVS or any other standard. This page is an internal alignment note: for each practice group or chapter it points to controls that exist in the repository and lists what is missing. "Aligned" below means "there is a related control", never "conforms". It cites only the practice-group (SSDF) and chapter (ASVS) level; it does not restate individual requirements or levels. Readers must consult the standards themselves. Related existing material: [docs/STANDARDS-EVIDENCE-MAP.md](../STANDARDS-EVIDENCE-MAP.md), [docs/STANDARDS-PARTICIPATION-READINESS.md](../STANDARDS-PARTICIPATION-READINESS.md), [docs/SECURITY-ASSURANCE-READINESS.md](../SECURITY-ASSURANCE-READINESS.md).

Coverage legend: **Related control exists** / **Partial** / **Gap**.

## NIST SP 800-218 (SSDF) practice groups

The SSDF groups practices as Prepare the Organization (PO), Protect the Software (PS), Produce Well-Secured Software (PW) and Respond to Vulnerabilities (RV).

| Group                            | Related controls in this repository                                                                                                                                                                                                                                      | Status  | Gaps                                                                                                                                                     |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| PO Prepare the Organization      | Threat model and ADRs (`docs/THREAT_MODEL.md`, `docs/ADR-*.md`); security review notes (`docs/COMPANY-LAUNCH-SECURITY-REVIEW.md`); incident runbooks (`docs/security-ops/INCIDENT-RUNBOOKS.md`); CI as the automated toolchain (`.github/workflows/ci.yml`)              | Partial | No defined security roles with named people, no training records, no formal secure-development policy, runbooks never exercised                          |
| PS Protect the Software          | Git history; lockfile; secret scan in CI (`scripts/secret-scan.mjs`); production dependency audit in CI; evidence reports regenerated and byte-checked in CI (`npm run evidence:check`); signed Proof records; Vercel deployment protection used for the live run        | Partial | No signed releases or build provenance, most Actions pinned by tag not SHA, no SBOM, branch protection and review rules not evidenced in the repository  |
| PW Produce Well-Secured Software | Design records and invariants (ADR-004, ADR-008, ADR-009); strict input schemas; fail-closed Trust Kernel; adversarial suites (Break Authority, fault matrix); typed code, lint, format, 1,900-plus tests (`docs/TAKEOVER-AUDIT-M7-M25.md`); internal code review passes | Partial | No independent review or penetration test, no static analysis beyond lint and typecheck, rate limiting absent, database roles not separated (see review) |
| RV Respond to Vulnerabilities    | `SECURITY.md` and `security.txt` (draft disclosure policy); dependency audit; incident severity levels and runbooks; post-incident note outline (INCIDENT-RUNBOOKS.md)                                                                                                   | Partial | No managed intake mailbox yet (placeholder), no triage rota, no response-time commitment, no remediation tracking beyond the review document             |

## OWASP ASVS chapters

ASVS organises requirements into chapters; chapter names below are used in general terms. Verification level targets are **not** claimed and no level was assessed.

| ASVS chapter (topic)                      | Related controls                                                                                                                                         | Status  | Gaps (see SECURITY-ENGINEERING-REVIEW.md)                                                                    |
| ----------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- | ------- | ------------------------------------------------------------------------------------------------------------ |
| Architecture, design and threat modelling | Threat model, ADRs, Trust Kernel single decision path, execution boundary, updated threat model in this folder                                           | Partial | Not reviewed by an outside party; no data-flow diagram set maintained per release                            |
| Authentication                            | Bearer credentials stored as SHA-256 digest, constant-time compare, expiry, uniform failure; separate admin authentication; owner console sessions       | Partial | No MFA, no rotation of admin token, no credential binding, no rate limiting on guessing (F-02, F-06)         |
| Session management                        | Durable console sessions, CSRF and origin checks, session hash storage, absolute lifetime, request budget per session (`src/console-session-durable.ts`) | Partial | Demo access-code model; not designed as a customer login                                                     |
| Access control                            | Scope enforcement, per-agent and per-principal binding, tenant-scoped SQL, lifecycle suspension, Authority revocation                                    | Partial | No row-level security, single-tenant hosted composition, approvals not authenticated end to end (F-11, F-12) |
| Validation, sanitization and encoding     | Strict schemas, bounded bodies, regex-constrained identifiers, parameterised SQL, nosniff and CSP headers                                                | Partial | Not every adapter reviewed; CSP allows `unsafe-inline` for styles and scripts in `vercel.json`               |
| Stored cryptography                       | Ed25519 grants and Proofs, SHA-256 digests, AES-256-GCM for wallet instrument and setup tokens, key derivation from a bootstrap secret                   | Partial | Single signing key, no rotation or key ring (F-04), no KMS-held key                                          |
| Error handling and logging                | Stable reason codes, request IDs, evidence events, no secrets in responses by design                                                                     | Partial | Structured logging and alerting not wired (F-09)                                                             |
| Data protection                           | Data classification and retention architecture (`docs/DATA-PRIVACY-RETENTION.md`), minimised responses, secrets not in evidence                          | Partial | Retention schedules need legal review; no deletion job run                                                   |
| Communication                             | HTTPS via Vercel, `upgrade-insecure-requests`, provider calls to PayPal over TLS                                                                         | Partial | TLS configuration is the platform's; not independently tested                                                |
| Malicious code                            | Review, lockfile, dependency audit, secret scan                                                                                                          | Partial | No supply-chain attestation                                                                                  |
| Business logic                            | Authority conservation, one-time grants, replay protection, UNKNOWN handling, reconciliation, merchant binding, concurrency tests                        | Partial | Reconciliation scheduling absent (F-03)                                                                      |
| Files and resources                       | Not a file-upload product; body size limits                                                                                                              | N/A     | Not assessed                                                                                                 |
| API and web service                       | Versioned REST routes, OpenAPI (`openapi/`), schema validation, JSON only, structured errors                                                             | Partial | No rate limits (F-02); conformance of OpenAPI to every route not fully re-audited                            |
| Configuration                             | Configuration schema with fail-closed parse (`parseHostedConfig`), security headers, no secrets in repo, minimum admin-token length                      | Partial | Platform settings (deployment protection, firewall) are not captured in the repository                       |

## How to use this page

- Do not quote it as compliance. Use it to plan work: each Gap links to a finding with a recommended fix.
- If a customer asks "are you SSDF/ASVS compliant", the accurate answer today is: no assessment has been done; here are the related controls and known gaps.
- Any future assessment (internal self-attestation, independent audit, certification) must be recorded as a separate dated artifact with scope, assessor and exact commit SHA. Do not edit this page into a claim.
