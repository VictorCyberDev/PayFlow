# M18 — A2A: constrained delegation

Status: **COMPLETE_LOCAL**. Real PostgreSQL and real HTTP through the hosted Gateway; no external A2A peer, framework or
hosted agent has been used, and nothing is deployed.

## What a delegation is

A row in `delegations` (migration 024, additive): a grant from a parent agent to a child agent that is narrower than or
equal to its parent on every axis (action kinds, currencies, counterparties, per-chain amount cap, expiry, depth ≤ 5).
It decides only whether a request may be **presented** to the Authority. The Authority, Trust Kernel, reservation,
grant, rail and Proof are unchanged — the delegated agent still acts under its own credential and Authority, and a
delegation can only add a constraint, never widen anything.

## Guarantees and where they are tested

| Guarantee                                                                             | Test                                                         |
| ------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| Multi-hop attenuation: each hop can only narrow (6 widening kinds + broken chain)      | `m18-delegation.integration.test.ts`                         |
| Shared budget conservation: 60 concurrent spends over a 4-leaf tree → exactly 20 pass  | same (parent spend == sum of children for every node)        |
| A tighter ancestor binds descendants whose own cap is larger                          | same                                                         |
| Revocation of a middle hop stops it and everything below; siblings and parent unaffected | same                                                      |
| Nonce cannot be reused; depth capped; a double release cannot mint budget             | same                                                         |
| Over real HTTP: pays once, charges the whole chain, next request refused by budget    | `m18-a2a-hosted.integration.test.ts`                         |
| Known-zero-effect DENY returns the budget; **UNKNOWN keeps the charge**               | same                                                         |
| Revoked chain stops before the Gateway or provider is touched                         | same                                                         |
| Replayed message id is a 409 and is not double-charged                                | same                                                         |
| A delegation cannot be borrowed by another agent; invented ids and inline scopes fail closed | same                                                  |

Mutation checks: removing the row lock (`FOR UPDATE`) fails the concurrency test on every run; removing the replay
release or the DENY release each fails its test.

## Design points worth knowing

- Chain rows are locked root-first and **read after the lock**, so two requests along shared ancestors serialize and
  cannot both pass a cap check.
- Budget is held under uncertainty: an UNKNOWN or completed action keeps its charge. Only a result with
  `effectCount === 0`, a front-door refusal, or a duplicate message gives it back.
- Peers never supply a parent scope. Inline (peer-presented) delegation is refused on the hosted host; only stored
  chains are honoured. A request without a delegation is simply governed by its own credential's Authority.
- A delegation can accompany only an exact `purchase` request; the amount, currency and merchant are read from the
  request and an unreadable one is refused (no guessing).

## Interfaces

`GET /v1/a2a/agent-card.json`, `POST /v1/a2a/message:send` (A2A 1.0 HTTP+JSON, synchronous; no streaming, push or task
persistence is advertised). Enabled with MCP on an https or loopback origin.

## Not claimed

- No external A2A peer or framework has interoperated; the agent card has not been checked by an independent client.
- There is no API to create delegations for a tenant yet (tests use the registry directly). Who may issue a root, and
  member-facing screens, are not built.
- The public Neon database has migrations through 023 only; 024 must be applied before this is usable there (runbook).
- Task persistence, streaming and push notification are not implemented.
